# Internationalisation

English and Turkish, via **next-intl 4**. Both are first-class; neither is a
bolt-on translation layer.

## Routing

|         |                                            |
| ------- | ------------------------------------------ |
| Locales | `en` (default), `tr`                       |
| Prefix  | **Always**, for both — `/en/…` and `/tr/…` |
| Root    | `/` → 307 → `/en`                          |
| Slugs   | **Translated per locale**                  |

```
/en/products/urea                      /tr/urunler/ure
/en/services/logistics-distribution    /tr/hizmetler/lojistik-dagitim
/en/about                              /tr/hakkimizda
/en/imprint                            /tr/kunye
```

Turkish visitors get Turkish URLs, not English paths behind a `/tr`. It reads
native and it indexes properly.

## The two sources of truth

**`src/i18n/routing.ts`** — the `pathnames` map. Route _shape_ per locale.

**`src/content/`** — the slug _values_ per locale, on each entity:

```ts
{ id: "urea", slug: { en: "urea", tr: "ure" }, … }
```

`tests/routing.test.ts` asserts the two stay in sync, that slugs are unique and
URL-safe, and that no Turkish path was left identical to its English one.

## Navigation

Always import from `@/i18n/navigation`:

```ts
import { Link, useRouter, usePathname, getPathname } from "@/i18n/navigation";
```

ESLint blocks `next/link` and the `next/navigation` hooks, because those bypass
the pathname map and produce untranslated URLs.

`LocaleSwitcher` re-resolves the _current_ route for the target locale, so
switching on `/en/products/urea` lands on `/tr/urunler/ure` — not the homepage.

## Adding a UI string

1. Add the key to **`messages/en.json`**.
2. Add the same key to **`messages/tr.json`**.
3. Use it: `const t = useTranslations("nav"); t("products")`.

Skipping step 2 is a **`pnpm typecheck` failure**, not a runtime surprise — the
`satisfies` guard in `src/i18n/messages.ts` makes English the required shape.

`tests/i18n.test.ts` additionally rejects empty values, `TODO` placeholders, and
Turkish sentences left byte-identical to the English.

## Adding a route

1. Add it to `pathnames` in `src/i18n/routing.ts`, with both locales.
2. Create `src/app/[locale]/<route>/page.tsx`.
3. Export `generateStaticParams` returning every locale.
4. Call `setRequestLocale(locale)` — without it the route silently goes dynamic.
5. Build metadata with `buildPageMetadata` from `@/lib/seo`.
6. Add it to `src/app/sitemap.ts`.

For a dynamic route, pass **`paramsFor`**, not a fixed params object:

```ts
paramsFor: (loc) => ({ slug: product.slug[loc] });
```

A single shared params object was an actual bug here: every alternate resolved
against the English slug, and the Turkish `hreflang` silently disappeared.

## Turkish copy rules

- **Never machine-translate.** Fertilizer and trade vocabulary is domain
  specific (_üre_, _amonyum sülfat_, _navlun_, _gümrükleme_); a literal
  translation reads foreign and costs credibility with the buyer.
- Long-form Turkish copy is written by the client. Until it arrives, the field
  is `tr: null` in the content layer — an explicit, countable state. `localize()`
  falls back to English so nothing renders blank.
- **Turkish runs 15–25% longer than English.** Check every section at 320px in
  Turkish before calling it done.
- Turkish has a dotted/dotless i (`i`/`ı`, `İ`/`I`). Never uppercase Turkish
  text in JavaScript; use CSS `text-transform` so the browser applies the
  locale's casing rules.
